## Architecture

`https://music.hollow-court.com` is a separate Cloudflare Access self-hosted application, not an added path on the game-admin application. This update preserves its existing music Access application and allow policy; the original September rollout used a host-only email policy. Add invited reviewers' exact email addresses only when supplied by the host; use a separate music reviewer policy, not the game-admin policy, when expanding access. Access email one-time PIN uses the existing team login method. This application has its own audience (AUD). The existing `/host` and `/api/admin` policy and audience on `hollow-court.com` remain scoped to game administration.

Cloudflare Tunnel points the music hostname to `http://lab:8765` on the Compose network. Neither Compose service publishes a host port. The lab independently checks the Access JWT signature, issuer, audience, expiration and identity on every HTTP request. **Shared decisions** come from the host's Keep/Cut/Maybe, or the latest active reviewer vote when the host is unrated. `feedback` is the canonical shared table; original/personal host choices are in `host_feedback`, reviewer choices in `reviewer_feedback`. Individual notes, listening scores and reviewer identities are not exposed to other guests. The host-only `/api/reviewers` report retains guest votes/notes; `/api/events` stays host-only. Votes never modify Spotify automatically.

The Mac running Docker must stay awake and online for the public URL to work. The local server at `127.0.0.1:8765` uses the old local database and is *not* the shared hosted state. Prepare provider enrichment in isolated ignored databases. For appends of entirely new review batches, use the [atomic live import](#append-a-new-batch-without-interrupting-review) below. Other `lab.py`, `enrich.py`, `youtube.py` or host-side operations that merge/rewrite hosted records still require stopping the lab first; the live append exception does not authorize those writers against the running database.

## Append a new batch without interrupting review

`import_batch.py` is a local maintenance utility, with no HTTP endpoint or authentication changes. It accepts one explicit room/batch, distinct new canonical Spotify IDs and contiguous ranks; it rejects feedback in the payload, reused room/batch IDs, existing IDs, orphaned feedback and an unexpected existing track count. Prepare and audit a complete enriched portable seed before running it.

Copy the utility into the already-running lab container and run it there, feeding the reviewed JSON on stdin. From `music/playlist-lab`, the command shape is:

```sh
docker compose cp import_batch.py lab:/tmp/import_batch.py
docker compose exec -T lab python /tmp/import_batch.py \
  --database /data/library.sqlite3 \
  --backup /data/backups/UNIQUE-BEFORE-BATCH.sqlite3 \
  --room living-room --batch NEW_BATCH_ID \
  --expected-count 50 --expected-existing PREVIOUS_TRACK_COUNT - < ../living-room/REVIEWED-BATCH.json
```

Replace every placeholder after checking the current library; never overwrite a backup or blindly retry an ambiguous result. No rebuild, stop or restart is needed. Restarting the server rotates its CSRF token and would require already-open review pages to reload before saving again.

The utility creates a restricted **0600 online SQLite backup**, then uses `BEGIN IMMEDIATE` to serialize a short append transaction with active voting. It checks every old serialized track, canonical/shared and personal host vote, note, reviewer score, settings row and snapshot inside that transaction, preserves old events as a prefix, adds exactly the new rows plus one import event, checks integrity and commits atomically. Any failure rolls back the entire append. Votes can legitimately advance between backup and transaction or after commit; the backup is not a license to overwrite later feedback. See SQLite's [online backup API](https://www.sqlite.org/backup.html) and [transaction isolation](https://www.sqlite.org/isolation.html).

Verify the new exact batch/order is unrated, the other room retains its current batch, and lab/tunnel container IDs and start times are unchanged. `test_import_batch.py` covers preservation with an open reader, concurrent Hollow voting, collision/count/batch guards, orphaned feedback and rollback after a mid-write failure. It does not simulate Cloudflare or provider playback.

## Security boundary and review

A focused configuration and code review on September 22 found no Docker host-port binding for either Compose service. The lab listens on port 8765 **inside** the Compose network; `cloudflared` makes outbound connections to Cloudflare and forwards only the music hostname to it. The Tunnel route requires the music Access audience and returns 404 for other hostnames. Anonymous public requests reached the music Access login. The lab also verifies the Access JWT signature, team issuer, music audience, expiry and email on every request; writes additionally require the exact HTTPS Origin and a CSRF token. The page now denies framing and suppresses referrers. The game-admin application has a different audience and was not widened.

This is a targeted review, not an independent penetration test. A process on the Mac or a container joined to the Compose network can reach the lab's HTTP port, but it still needs a valid music JWT to read or write. The separate old local server on `127.0.0.1:8765` remains unauthenticated and loopback-only; it uses a different database. Cloudflare remains the identity issuer and policy enforcement point; a stolen valid Access token could be replayed until it expires. An unapproved identity and a second approved reviewer have not yet been tested end to end. Keep the tunnel token and hosted database private.
