## Fresh runtime comparison

Measured October 24 on the host's Apple Silicon Mac, macOS 26.6.2, desktop Google Chrome 153, ONNX Runtime Web **1.30.0**. Both backends used the identical pinned **6,082,421-byte** f32 feature graph and the three existing private fox reference JPEGs. Preprocessing reproduced the production centre square covering 87.5% of the short edge, resized to 224px, with ImageNet mean/std.

Each backend started a new dedicated Worker and session. Each photograph ran nine times; the first inference is separate, leaving 26 warmed samples. Inference timings include CPU input transfer and CPU-accessible 1,024-value feature output, but exclude photograph decoding, resizing, normalization and gallery matching. Preparation includes loopback model fetch and session creation, excludes the runtime module import, and is **not** a real-network cold-download measurement. The raw samples below are exploratory, not controlled phone p50/p95 estimates; other desktop activity can affect them.

| Same MobileNet graph              | Session preparation | First inference | Warm median | Warm sample p95 |
| --------------------------------- | ------------------: | --------------: | ----------: | --------------: |
| Single-thread WASM CPU            |              836 ms |          172 ms |     56.8 ms |         69.7 ms |
| WebGPU, ordinary CPU input/output |            5,380 ms |          923 ms |     78.0 ms |        247.1 ms |

The two backends' normalized vectors agreed with cosine similarity above **0.999999999998** on all three photographs. That demonstrates numerical agreement for these inputs, **not** recognition accuracy or rejection of other objects. A second WebGPU experiment attempted static graph capture with persistent GPU input/output buffers and explicit CPU readback. It did not complete reliably (`undefined` buffer `size` inside the runtime), so it provides no usable timing or deployable recommendation. This may require harness/runtime integration work; it is not evidence that graph capture is universally broken.

Installed runtime binary sizes before HTTP compression are **14,239,897 bytes** for CPU WASM and **28,312,028 bytes** for WebGPU's JSEP WASM. The larger WebGPU binary also exceeds Cloudflare's individual 25 MiB static-file limit and would need explicit packaging/streaming, as the older experimental GPU runtime did. These are file sizes, **not peak memory measurements**. No new iPhone/Android latency, battery, thermal or peak-memory measurement was made.

The private, loopback-only reproduction is `private/recognition-review-2026-10-24/serve.mjs`; run it from the app folder and open `http://127.0.0.1:5189/`. Its allowlist serves only the benchmark, installed ORT runtime files, this model and the three private fox fixtures. Each runtime button starts a fresh Worker; Stop terminates it. Reports and vectors stay in the ignored folder. Do not expose this server or commit its photographs/vectors. No npm dependency was added.

## Where the apparent scan time goes

Current production code samples serially at up to **4 Hz**, while the camera targets **12 fps, capped at 15**. It deliberately requires **three consecutive matching frames spanning at least 500 ms**. Unknown, ambiguous and changed identities reset that streak. A 50 ms model does not make this a 50 ms encounter: its first inference plus that confirmation span already approaches roughly 550 ms, before frame capture and reveal work.

At the start of this review, the host fox could spend **850 ms** on optional saved-view fetching/ORB entrance alignment before its character mounted. This revision prefetches fox poses during host Lens preparation and caps the combined cosmetic fetch/match wait at **200 ms**. Slow/uncertain alignment falls back to the centre. This reduces the worst-case optional wait by **650 ms** without changing identity acceptance, the three-frame stability rule, camera shutdown or the standard final pose. It is a reveal-path optimization, not a faster recognition-model claim.

## Current alternatives and practical fit

| Option                                                   | Assessment for our fifteen props                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Same MobileNet on WebGPU                                 | Tested above; no desktop speed benefit and more runtime download/init work. Keep CPU default. Static graph capture requires persistent external GPU buffers and careful lifecycle handling; it is not simply an execution-provider switch.                                                                                                                                                                                                                                                                                                              |
| LiteRT.js with the same encoder                          | The most interesting newer **runtime** experiment: Google released it July 9, 2026, with XNNPACK CPU/WASM and WebGPU. Convert the exact encoder and validate numerical parity before comparing. Its published speedups are vendor benchmarks on an M4 Mac, not our phones or this graph. No conversion or LiteRT benchmark completed here. [Google announcement](https://developers.googleblog.com/litertjs-googles-high-performance-web-ai-inference/), [current conversion/runtime guide](https://developers.google.com/edge/litert/web/get_started). |
| MobileCLIP2-S0                                           | Relevant for reference-image embeddings, but its image encoder has 11.4M parameters versus our small pruned graph. Roughly 45.6 MB of f32 image weights before packaging is a parameter-count estimate, not a measured export. Apple's native iPhone timings do not establish browser speed. Screen for accuracy only if our held-out photos reveal failures. [Official implementation and model table](https://github.com/apple-aiml-research/ml-mobileclip).                                                                                          |
| DINOv3 ViT-S/16                                          | Strong visual features, but the smallest official ViT is 21M parameters; not an obvious speed/download improvement. No new benchmark or guardian accuracy claim. [Meta implementation/model list](https://github.com/facebookresearch/dinov3).                                                                                                                                                                                                                                                                                                          |
| YOLOE-26 visual prompts                                  | Uses reference regions rather than generic labels, so conceptually relevant. Already tested October 23: the derived 10.6 MB CPU export took approximately 2.2–2.3 seconds and missed one of three fox views. Export bakes visual classes, complicating live reference uploads. No reason to replace the working matcher with it now. [Official prompting/export documentation](https://docs.ultralytics.com/models/yoloe/).                                                                                                                             |
| Fine-tune a tiny encoder/classifier for the fixed roster | Possible because all fifteen props are known. It primarily targets confusing objects, not guaranteed speed. Needs real varied photographs, backgrounds and held-out clips; three fox references cannot validate it. The current reference matcher is already cheap to update without retraining.                                                                                                                                                                                                                                                        |
| SAM/EdgeSAM/EdgeTAM                                      | Segmentation/tracking are different tasks from guardian identity. Their cost is unnecessary for the new authored 3D performance; keep them out of the fox recognition path. See the existing October 23 measurements.                                                                                                                                                                                                                                                                                                                                   |

[WebKit confirms Safari 26 ships WebGPU](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/), including iOS. Browser API availability is distinct from inference-runtime/operator compatibility: [ORT's current support matrix](https://onnxruntime.ai/docs/get-started/with-javascript/web.html) still lists Safari/iOS WebGPU unsupported, while WASM is supported. Do not require a guest browser flag, LiDAR, Apple Neural Engine access or a Pro phone. [ORT explicitly recommends WASM for very lightweight models](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html) and documents graph capture's static-shape/all-kernel requirements and GPU I/O costs.

## Promotion gate

Before any model/runtime replacement, hold enrollment photographs separate from evaluation. Enroll the actual fifteen props with front/side/back and party-light views; reserve new photos and clips with clutter, occlusion, distance changes, other guardians, empty shelves and ordinary decorations. Compare correct identity, false wake-ups, unknown rejection, warm stable-match time, cold preparation, download and repeated-scan stability on iPhone Safari/Chrome and ordinary Android Chrome. Keep the current 0.80 similarity, 0.04 distinct-guardian/background margin and temporal confirmation as the baseline; similarity is not probability.

Use photographs of the real props for recognition. The cute authored characters are appearance references and performance assets; rendered synthetic views alone do not validate recognition of real materials in room lighting. Ship a replacement only when it improves the actual phone experience without sacrificing rejection or introducing a large new download.
