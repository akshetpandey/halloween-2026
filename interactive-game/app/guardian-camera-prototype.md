# The Looking Lens — guardian camera prototype

Updated October 23, 2026. The host authorized live camera discovery as a possible NFC replacement. The current revision uses a small, warmed recognizer and continuous frame extraction. Existing puzzles, Favor validation, NFC routes and the public time gate remain in place. [Live revision handoff](handoff-2026-10-23-live-lens.md) · [Earlier captured-photo build](handoff-2026-10-23-guardian-camera-prototype.md). Actual-prop/phone acceptance is still open.

The host reported iPhone Chrome crashing immediately after test initialization. The earlier SlimSAM path reached **1,968 MiB** peak process RSS in a controlled local CPU run. The current build uses **MagicTouch 512px** instead, via a dedicated MediaPipe CPU Worker. Recognition remains MobileNet and saved reference features do not need refreshing for this change. [Crash fix evidence](handoff-2026-10-23-host-crash-fix.md). Earlier SAM/WebGPU notes in historical handoffs are superseded.

## Start testing

Use the [phone walkthrough](guardian-phone-test.md) for a first test with a few references, held-out photos, live scanning and the complete onboarding flow.

1. Open the [host dashboard](https://hollow-court.com/host?tab=guardians), sign in with the existing host account, and select **Guardian reference photos**.
2. Choose the character for a physical guardian. Upload front, left and right photographs to begin. Centre the entire object inside the middle square, with some space around it. Add varied distances and actual party lighting; aim for 10–20 useful views, maximum 40 per guardian. Use ordinary phone photos, not the website illustrations.
3. Add **Room backgrounds · not a guardian** examples: empty shelf, nearby decoration, ordinary objects. Enroll at least two distinct guardians before judging rejection.
4. If photos were saved with the first prototype, choose **Refresh saved views** for each guardian and background group. This recomputes features locally from the retained private originals. No re-upload is needed. Old feature vectors are excluded from matching until refreshed.
5. Choose **Test the Looking Lens** and wait for **Lens ready · awakening ready**, then choose **Open the live lens**. Allow camera access and centre one object in the square. It samples up to four frames per second, requires three consecutive matches spanning at least half a second, then captures a frame and wakes the guardian automatically. No shutter tap is needed. **Choose a photo** also accepts an unused photo of the object for a quick test.
6. The greeting and trial button appear immediately after recognition. The outline runs separately; its cutout glows when ready. The fox pilot adds a small head tilt and tail swish; other guardians retain the floating reveal. Guests can enter the puzzle while it is still outlining. Tap the creature to refine the outline, or skip it. Only solving the puzzle earns Favor.

Host diagnostics show recognition preparation, awakening preparation, per-photo outline inference, per-frame processing, number of sampled frames and time to a stable match. Live camera tests also report camera opening time (including any permission prompt), tap-to-preview readiness and whether an earlier device selection was available as a hint. Recognition and segmentation use separate CPU Workers, prepared sequentially; the heavy SAM/WebGPU comparison has been removed. **Test a video** runs a local clip through the same video/frame loop without a webcam; it never uploads the clip. Photo selection and the native phone camera remain fallback options.

Guest rehearsal: [Workers preview](https://hollow-court-preview.computer-toolbox.workers.dev) → **Field notes → Looking Lens · camera prototype**. Registered rehearsal guests also have a Lens button on the Court homepage. Guest `/scan` and vision APIs remain unavailable on the public domain during this pilot. Access-protected host enrollment/testing works before the event opens.

## Phone and real-prop acceptance

Normal RGB photos are sufficient to test. iPhone 16 Pro LiDAR is optional future asset work, not a guest requirement. This implementation consumes no depth or mesh data. A textured [Apple Object Capture](https://developer.apple.com/documentation/realitykit/capturing-photographs-for-realitykit-object-capture) asset could later supply 3D animation or extra reference angles.

Reserve separate held-out views and clips for each real object: front/sides, close/far, bright/dim/party lights, clutter and partial occlusion. Test other guardians and ordinary objects too. Record correct matches, wrong matches, rejections, cold preparation, warm match time and mask quality. Repeat in iPhone Safari and Chrome on an ordinary Android. A Mac viewport/video fixture does not establish phone accuracy or performance.

Defaults are **0.80 cosine similarity** and **0.04 lead** over another guardian/background. These are starting settings, not probabilities or measured accuracy. Improve reference coverage before lowering them. The host can adjust both in Calibration and pause individual guardians. Uncertain frames reset the match streak; the scanner keeps looking instead of guessing.

The effect is a captured-frame 2D awakening after live recognition. It is not a continuously tracked mask or an articulated 3D creature. Segmentation can still take several seconds on CPU; it does not gate the trial. First use must download and initialize the runtime/models; weak network conditions can still delay readiness. Recognition preloads and runs its warm-up during name/selfie onboarding and recovery entry, followed by segmentation, without blocking either flow. Returning rehearsal guests warm on session restoration too. MagicTouch runs a synthetic 512px warm-up, releases its output masks and retains one CPU model. It does not segment the guest's selfie. The page keeps separate shared recognition and segmentation workers across the Court, puzzles and Lens visits; opening the camera reuses them. Leaving the Lens clears its working image while keeping the models warm. If preparation is still running, the Lens joins that same operation. Caught failures can be retried. If a reload/process crash interrupts outline work, a tab-scoped marker prevents automatically repeating it on the next load: recognition remains available, with **Retry awakening outline** for an explicit retry. A full page reload otherwise needs initialization again (cached files can still be reused). The sealed public entrance and host guest book do not initiate this preload. **Lens ready · awakening ready** confirms both models are prepared. See the [segmentation-prewarm handoff](handoff-2026-10-23-segmentation-prewarm.md) and [earlier arrival-prewarm handoff](handoff-2026-10-23-arrival-prewarm.md).

## Implementation and privacy

- **Fox photo puppet:** a bounded 40×40 textured mesh uses the existing cutout to tilt the head and swish the tail independently, with a stationary body. A small WebGL 1 renderer adds no model/dependency download and draws at most 24 frames per second. It pauses while hidden, respects reduced motion, offers **Let it rest / Wake it again**, and releases the texture, geometry, context and frame loop on exit. Unsupported/lost graphics contexts retain a static glowing cutout. This is 2D image deformation, not generated video or automatic animal pose estimation; no photo is sent to another service. The default silhouette heuristic targets the pilot's upright-tail fox. In the host test, **Adjust fox movement** lets the host place Head, Neck, Tail tip and Tail base in the captured photo. Those adjustments last only for that capture; they are not saved to references or mapped across new camera views. [Implementation and checks](handoff-2026-10-23-fox-puppet.md).
- **MobileNetV3 small, full precision**, pinned to [onnx-community revision b1a19675](https://huggingface.co/onnx-community/mobilenetv3_small_100.lamb_in1k/tree/b1a19675d33130739e56503b5bfd6534a0f9e01d). The ImageNet classifier is pruned, exporting normalized 1024-value penultimate features. Centre crop covers 224/256 of the short edge; input is 224px RGB with ImageNet normalization. The smaller q8 candidate was rejected after poor transformed-image matches; full precision was faster and more consistent in the Mac fixture checks.
- Best-reference cosine matching aggregates by distinct guardian; another view of the same guardian cannot become its own runner-up. Background examples participate in rejection. Model/version guards prevent mixing incompatible features.
- Camera frames are sampled serially, with one transferable ImageBitmap in flight and no frame queue. The Worker resizes directly to 224px. Duplicate video times are skipped; unknown identities or long pauses reset stability. Page-owned drawing surfaces reuse their allocation at unchanged geometry, with a 960px long edge for recognition and 1280px for capture. They are cleared when scanning stops, so blank buffers rather than previous frames survive navigation.
- The page remembers only the last successful camera's device ID in memory, as an **ideal** hint on the next explicit open. IDs can rotate and unavailable devices remain optional. No enumeration or camera request runs during onboarding, while idle, or on returning to the Lens. Camera capture requests no microphone, targets 1280×960 at 24fps with a 30fps cap, and fully stops every track at capture/reset/navigation/backgrounding/page hide. Even a pending permission request is invalidated; a stream that arrives after cancellation is stopped immediately. The page does not retain a hidden/disabled track to keep the sensor warm. [Stopping tracks](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/stop) releases their source; [the media capture lifecycle](https://www.w3.org/TR/mediacapture-streams/#life-cycle-and-media-flow) makes physical camera/indicator behavior browser-controlled. Hardware startup latency still remains when reopening. See [camera lifecycle verification](handoff-2026-10-23-camera-reuse.md).
- **MagicTouch 512px CNN**, pinned Google model version 1, SHA-256 `e24338a717c1b7ad8d159666677ef400babb7f33b8ad60c4d96db4ecf694cd25`. It segments the object at the centre/tap point. Source images are bounded to a 512px long edge before inference; masks are copied inside the synchronous callback and MediaPipe releases its transient results. Very small or full-frame masks are rejected. Only the current bounded working image remains for tap refinement, and is cleared on Lens exit/reset. [Google model card](https://storage.googleapis.com/mediapipe-assets/Model%20Card%20MagicTouch.pdf).
- **MediaPipe Tasks Vision 1.1.1**, CPU delegate, in a dedicated module Worker with self-hosted pinned ES-module WASM loader/binary. The explicit legacy API uses the small 512px model; Google's newer stateful API requires a different 768px model and is not silently substituted. No segmentation request reaches the ONNX recognizer or the retired SAM graph.
- **ONNX Runtime Web 1.30.0** runs the unchanged MobileNet recognizer with one WASM thread. Neither model requires cross-origin isolation. The recognizer graph is **6,082,421 bytes**, its CPU runtime about **14.2 MB raw** before HTTP compression. MagicTouch adds **6,227,884 bytes** of weights, a **13,519,940-byte** WASM binary and its loader. Browser caching avoids repeat downloads; the public locked homepage loads none of these assets. Historical DINO/SAM/GPU assets remain for old-cache compatibility but current clients do not request them.
- Host photos are re-encoded as JPEG, maximum 1024px edge, then saved to private `PHOTOS` KV without expiry. Features/settings are in D1. Migration `0006_guardian_vision.sql` creates enrollment storage; `0007_fast_vision.sql` preserves all existing rows/originals while allowing both legacy 384-value and current 1024-value vectors. The Worker accepts only the current model for enrollment/refresh.
- Reference originals require Cloudflare Access plus Worker JWT verification. Registered rehearsal guests receive only IDs, features and settings. Reference notes, original photos and NFC route codes are excluded. Guest frames/photos/masks/videos remain in browser memory; no recognition cloud API is called.
- Recognition is not proof of physical presence; a shared NFC URL could also be opened remotely. The existing server validates puzzle solutions and enforces unique Favor awards. Host reference removal is separate from the removed guest account/portrait deletion flow.

## Reproducible assets and checks

`npm run build` downloads pinned sources with SHA-256 validation, deterministically prunes the MobileNet classifier using the official ONNX schema, checks the derived checksum, writes licenses/manifests, type-checks and builds Vite. `scripts/prepare-fast-vision.mjs` records the new source and output hashes. Weights stay in ignored `public/models/`; private photos, fixture keys and runtime data stay out of Git. MobileNet, MagicTouch and MediaPipe are Apache-2.0; ORT is MIT. Retained historical DINO assets include Meta's separate license.

Current model/runtime files fit the [25 MiB static-file limit](https://developers.cloudflare.com/workers/platform/limits/). The old GPU runtime streaming route remains only for compatibility. Successful versioned model/runtime URLs are immutable for a year. The Worker supplies a binary content type when Static Assets omits ONNX/TFLite MIME metadata, so model downloads can actually stay in browser cache. HTML fallbacks/errors never receive model caching. HTTPS, HSTS, CSP, private API caching and existing host protections remain.

```sh
npm run db:local
npm run build
npm test
# Local Worker + signed host JWT fixture configured as described in README:
npm run test:integration
node scripts/check-vision-models.mjs /absolute/path/to/test-image.jpg
npx wrangler deploy --dry-run
# Apply migration 0007 before publishing the current Worker:
npx wrangler d1 migrations apply DB --remote
npx wrangler deploy
```

Restart local Wrangler after each production frontend rebuild if its static watcher is disabled. Tests cover matching/rejection, temporal stability, interrupted-outline recovery, CPU worker isolation, bounded images/mask cleanup, private originals, current/legacy vector validation, refreshing saved photos, disabled guardians, cache policy and no Favor for recognition. The CLI smoke checks recognition; the retired SAM comparison requires an explicit `--legacy-sam` flag. Browser photo/video tests exercise actual MagicTouch warm-up, refinement and reuse. Neither establishes real guardian/phone accuracy.
